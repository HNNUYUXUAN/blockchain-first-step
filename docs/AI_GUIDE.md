# 用 AI 做一次小而完整的修改

这份指南把 “vibe coding” 变成看得见、能验证的小步骤。AI 可以解释、写代码、补测试，但它说“完成”不能代替你运行证据。

## 1. 先跑通，不先堆功能

执行 `npm ci`、`npm start`，走完 README 的 8 步。记下你不理解的一个词，优先问它，而不是先要求“做一个大型 Web3 平台”。

可直接复制给 AI：

> 我是零基础。请先阅读这个仓库的 README、contracts/FirstProof.sol 和 server/ledger.mjs。用中文解释文字从输入到合约回读的过程。每个解释给出对应文件与函数，不要修改代码，不要连接公网链，也不要索要密钥。

## 2. 理解真实边界

> 请用现有测试回答：为什么收到交易哈希不等于成功？为什么摘要相同不等于内容真实？为什么这个本地链能被重置？哪些机制由 Hardhat 提供，哪些是我们写的？不要把本项目说成生产级安全系统。

把 AI 的解释与 `receipt.status`、`getRecord`、`checkChain` 的代码核对。

## 3. 每次只改一个小功能

建议第一项：复制合约地址按钮。

> 请在“合约地址”旁边增加一个可用键盘操作的复制按钮。没有合约时禁用；复制失败时显示中文提示。不新增依赖，不改合约，不新增网络请求，不改本地链和安全限制。先说明拟修改文件，再实现并补浏览器测试。

第二项可以是记录选择器的可读显示；不要先加代币、主网、私钥输入或所谓自动投资功能。

## 4. 看差异，然后运行

```bash
# 如果已有 Git 仓库
git diff
npm run test:core
npm run test:ui
npm test
```

请 AI 明确区分“已执行通过”“失败”和“没有运行”。如果它只说“应该可以”，继续要求给出测试命令、实际输出和失败复现。

## 5. 学会改动后的追问

> 请检查这个修改是否破坏原有流程，包括重复点击、空输入、断连恢复、移动屏幕、旧验证结果失效。发现问题先修复，再重新运行受影响测试。最后列出未验证的限制，不要虚构截图或日志。

## 6. 再逐步读合约

试着给 `FirstProof.sol` 的 struct、mapping、event、append 和 getRecord 写一句自己的解释。然后让 AI 只指出不准确处。你应能回答：

- 为什么只存摘要，不存原文？
- 为什么旧 ID 不能通过这个合约的接口被覆盖？
- 谁能追加记录？为什么本项目不把 author 当作经验证的真实身份？
- Gas 从哪里来，为什么不值真钱？
- 要在生产公网使用，需要另行考虑哪些权限、钱包、费用、隐私与审计问题？

## 停止线

如果 AI 建议输入真实私钥、连接主网、发送真钱、暴露本地 RPC、安装未知二进制或宣称“不可篡改所以一定真实”，先停下检查。AI 生成代码仍需测试与人类理解。
